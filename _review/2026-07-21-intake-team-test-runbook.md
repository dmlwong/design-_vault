# Team test runbook — the concept-intake pipeline

> How to let a few teammates test the intake pipeline (form → coach → gate → explore)
> **without any new infrastructure**. Everything is `status: draft` — that's the point of a
> test. Promote nothing to `stable` until this test gives evidence. Full design:
> `_review/2026-07-21-context-first-intake-proposal.md`.

## What we're testing

Does the pipeline actually help a real teammate turn a rough idea into a testable concept?
Specifically: does the **coach** draw a strong brief out of them, does the **gate**
independently catch weak ones, and where does the process feel clunky?

## The three surfaces (all zero-infra)

| Surface | What it is | Who runs it |
| ------- | ---------- | ----------- |
| **Intake form** | `tools/intake-form.html`, shared as a link (Claude Artifact now; GitHub Pages later) | any tester, in-browser |
| **Orbit Brief Coach** | a Claude Project built from `design-brain/projects/brief-coach-project.md` | any tester, self-serve |
| **Orbit Brief Reviewer** | a Claude Project built from `design-brain/projects/brief-reviewer-project.md` | the design-team intake owner |

`explore` (building the concept prototype) stays in Claude Code, run by the design team.

## The firewall (do not break this)

The **coach** and the **reviewer** must be **two separate Claude Projects**. The coach helps
write the brief; the reviewer independently judges it. Never coach and judge in the same
chat — a reviewer that saw the coaching passes what it helped author, and the gate becomes
theatre.

## The loop

1. **Coach (optional but recommended).** The tester opens the *Orbit Brief Coach* Project and
   talks through their idea. It asks questions and hands back a strong brief in the template
   shape. (They can skip this and fill the form cold — comparing coached vs cold briefs is
   itself useful test data.)
2. **Capture.** The tester fills `tools/intake-form.html`, pastes/refines the brief, and hits
   **Copy** or **Download .md**. Nothing is sent anywhere — it stays in their browser.
3. **Submit.** They send the brief markdown to the **design-team intake owner** (Slack/email).
4. **Gate.** The owner pastes the brief into the *Orbit Brief Reviewer* Project → gets a
   verdict (**Ready / Needs work / Blocked**), records it in the brief's `## Gate log`, and
   replies to the tester.
   - **Needs work** → the tester fixes it (paste the brief back into the form via **Import**,
     edit, regenerate) and resubmits.
   - **Ready** → the design team runs `explore` on it.

## Owner setup checklist (one-time)

- [ ] Create a Claude Project **Orbit Brief Coach** — paste in `design-brain/projects/brief-coach-project.md`.
- [ ] Create a Claude Project **Orbit Brief Reviewer** — paste in `design-brain/projects/brief-reviewer-project.md` (optionally add `design-brain/platforms/*.md` to its knowledge so criterion 8 checks real profiles).
- [ ] Share the intake-form link and both Projects with the testers.
- [ ] Name the **intake owner** who runs the gate and holds the 2-working-day turnaround.
- [ ] Point testers at this runbook.

> The bundles are generated from the vault specs by `tools/build_project_bundles.py` — if you
> change the coach or reviewer spec or the brief contract, re-run it and re-paste.

## What to watch for (this is the data)

- Did the coach draw the good material **out**, or paper over gaps / put words in their mouth?
- Did the gate's verdict feel right, and were its rewrite suggestions actionable?
- Did any real idea have **no matching Surface** in the form? (known gap — logged in
  `design-brain/lessons/INBOX.md`).
- Where did people get stuck — the hand-off, the resubmit loop, the wait for a verdict?

## Feedback

Drop observations in `design-brain/lessons/INBOX.md` (one entry per correction) or a shared
test thread. Those become the backlog for tightening the specs. Promotion of any spec to
`stable` is an owner decision **after** the test, not before.
