# Lessons Inbox

Low-friction capture for the feedback loop (`AGENTS.md` §6). When a human corrects an
agent's wrong assumption about Orbit **mid-task**, the agent appends an entry here and
continues — instead of stopping to edit the brain file immediately. The
`vault-librarian` triages entries into proposed edits; the owner approves; the entry is
deleted when the fix lands in the canonical file. **This file must trend toward empty.**

Governed files (tokens, contracts, `AGENTS.md`, defaults, projections) are never edited
directly from here — entries against them become change requests
(`_review/Change Request Template.md`).

## Entry template

```
### YYYY-MM-DD · <task, one line>
- Wrong assumption: <what the agent believed>
- Correction: <what is actually true — quote the human where possible>
- Proposed target: <the brain file that should change, and roughly how>
- Status: new | triaged | approved
```

## Where an applied lesson lands

Triage sends a correction to one of two homes, and the second is easy to forget:

1. **A canonical brain file** — when the lesson changes a rule, a default, or a contract.
2. **A trap on the agent that made the mistake** — when the lesson is a recurring, mechanical
   error rather than a rule change. Traps live next to the instruction they modify, dated to
   the incident that produced them (`design-brain/agents/brief-reviewer.md` "Common brief
   traps", `design-brain/agents/design-reviewer.md` "Dense table review traps").

An entry is deleted once its fix has landed in one of those two places — not when it is
merely agreed. Verify the fix is really there before removing the entry.

## Entries

### 2026-07-30 · Vault Health publishing — a doc promised a property no code enforced
- Wrong assumption: that `vault-health.html` was published sanitised, "carrying aggregate
  counts only and never internal file paths" (`CLAUDE.md`, Repository Facts). I reported it
  to the owner as a live leak, because the page publishes paths.
- Correction: the claim had been false in two different ways at different times. The
  `assert_clean()` guard in `tools/build_site.py` only ever checked a `BLOCKLIST` of proper
  nouns — it has never checked for file paths, so nothing enforced the promise on the day it
  was written. Then the 2026-07-30 rewrite made the health page `protected`: it now skips the
  sanitiser entirely, carries 59 repo paths by design, and is encrypted or omitted. The page's
  own footer was updated to say so; the prose describing the mechanism was not. Owner decision
  the same day: keep publishing the explainers' paths, and fix the claim rather than the guard.
- Proposed target: applied directly — `CLAUDE.md` Repository Facts, the `build_site.py`
  module docstring and `SANITISE` comment, a SCOPE block on `BLOCKLIST` stating that the
  guard covers proper nouns and deliberately not paths, and the `site-manifest.json`
  `_comment`. The generalisable rule, which is the part worth keeping: **when a mechanism
  changes, grep for prose describing the old one.** A rewrite that corrects the generated
  output can still leave every comment and doc around it asserting the previous design, and
  those are what the next agent reads first. Worth a line in
  `design-brain/orchestration.md` under the generated-projection doctrine.
- Status: new

### 2026-07-30 · Vault Health 404 — fail-closed left the nav pointing at the withheld page
- Wrong assumption: that omitting the unencryptable health page from the published site
  was the whole of failing closed. The owner hit a 404 and reasonably read it as breakage.
- Correction: `render_nav()` and `render_hub()` in `tools/build_site.py` rendered every
  manifest entry unconditionally, so all five published pages plus the hub advertised
  `health.html` — six links into a page `build()` had deliberately refused to publish.
  Withholding a page is only half the mechanism; everything that points at it has to
  reach the same verdict, or fail-closed presents as a broken site. Owner decision
  (2026-07-30): omit the entry entirely rather than show a dimmed placeholder.
- Proposed target: applied directly — `protected_publishable()` in `tools/build_site.py`
  now makes one publishability decision that the nav, the hub, and the staging branch all
  share, and the CI publish step treats an encryption failure after successful staging as
  a build failure instead of a warning. The generalisable rule: **when a mechanism
  withholds an artifact, every generated reference to that artifact must be derived from
  the same decision** — not from the manifest the mechanism overrides.
- Status: new
