# Write Stories

Produce a story set that enumerates a component's real surface — every variant, size,
state, and slot — so that `extract-contract` can derive the contract from observed
behaviour instead of guesswork, and so both themes are verifiable per story.

Coverage is the number this skill exists to move: see the live figure in
`tools/storybook-status.json` (`components_with_stories` / `components`).

## Workflow

### 1. Load the ground truth
Read, in this order:
1. The component source (`packages/orbit/src/**/<Name>.tsx`) — props, variants, states.
2. Its contract (`design-brain/components/<name>.md`) if one exists. Story names must use
   the contract's vocabulary. No contract → note it; the story set you write becomes the
   extraction input for one.
3. `design-brain/storybook.md` — **the seven enumeration rules in "How to write an
   extractable story" are the canonical spec for this skill. Follow all seven, plus the
   `argTypes` rule. Do not abridge them.**
4. The reference implementation: `packages/orbit/src/actions/Button.stories.tsx` —
   copy its shape (meta, autodocs, JSDoc, `AllVariants`, `Themes`).

### 2. Write the set
- One story per variant, per size/density, per state, per slot — named in the
  contract's vocabulary (`Secondary`, not `Story2`).
- Keep one `AllVariants` story (intent hierarchy side by side) and one `Themes` story
  (subtree wrapped in `data-theme="orbit"`, same mechanism as production).
- Constrain `argTypes` to the real options; disable controls for `ReactNode` slots.
- JSDoc on `meta` and each story: one sentence on *when to reach for this variant*.
- **Do not invent behaviour.** A story may only exercise props and states the source
  actually supports. A state the component lacks is a contract/gap finding, not a story.

### 3. Verify
- `npm run dev:storybook` — every story renders; flip the Theme toolbar on each;
  read the a11y panel (it is a floor check, not the accessibility contract).
- `npm run build:storybook` — the set compiles. CI's blocking `verify` job runs this
  plus the full test suite; a red `verify` is a stop, not a footnote.
- A green Storybook build does **not** prove the tests still pass — they are separate
  steps for a reason (see the `legacy-peer-deps` incident in `design-brain/storybook.md`).

### 4. Report
State plainly: stories written (count and names), variants/states/slots covered, anything
in the source that had no contract vocabulary to name it (→ contract-gap candidate), and
the new coverage figure.

## Hard stops
- An install conflict tempting you toward `legacy-peer-deps` → stop; declare the missing
  peer instead (`design-brain/storybook.md`, Known constraints).
- A variant or state you cannot reach through the public API → do not force it with
  internal hacks; record it as a gap.
- Bumping Storybook or Vite majors to "make it work" → stop and escalate; the pins are
  deliberate.
