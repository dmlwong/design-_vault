What it is

A shared brain, not a slide deck.

The vault holds the actual specifications our products are built to — written once, referenced everywhere, and kept honest by automated checks. It replaces scattered, conflicting guidance with one authoritative place.

01

Single source of truth

Designers, engineers, and AI tools all read the same contracts. No more "which version of the button is right?"

02

Two platforms, one foundation

Connected Platform (internal Efficio users) and Orbit / Client Connected Platform (external clients) share a base, and diverge only where they should.

03

Built for AI-assisted delivery

Machine-readable rules route each task to the right specialist agent — so AI builds to our standards instead of generic defaults.

04

Governed & self-checking

Changes go through review; CI catches broken links, missing metadata, and stale docs before they spread.

The orchestration layer

Eight specialist agents — each on the right-sized model.

Rather than one AI doing everything, work is split across specialists. The rule is simple: the more a task is pinned down in writing, the cheaper the model it needs; the more it depends on judgment, the stronger the model we put on it.

context-scoutHaiku

Assembles the context packet — which files, which platform, which agent a task needs.

vault-librarianHaiku

Link checks, metadata lint, staleness sweeps, triages the corrections inbox.

contract-extractorSonnet

Reads real source code and writes the component contract for it.

component-builderSonnet

Builds or refactors one component to its written contract.

screen-builderSonnet → Opus

Composes multi-component screens; steps up a tier when no pattern exists yet.

porterSonnet

Ports external / Lovable prototypes onto Orbit tokens and components.

design-reviewerOpus

Judges finished work against the brain — with fresh eyes, never grading its own build.

benchmark-judgeOpus

Blind A/B scoring for quality benchmarks — scoring integrity gate.

Haiku Sonnet Opus
More written constraint → cheaper model. More judgment → stronger model. The strongest model reviews the work — because rework costs more than review.

How a build task flows

Scout, build, review — then ship.

Step 01

context-scout

Reads the task, gathers the exact files and rules it needs.

›
Step 02

builder

Builds strictly to the contract — tokens only, every state, both themes.

›
Step 03

design-reviewer

Fresh context audits it against the brain. Any blocker sends it back.

›
Step 04

handover

Passes checks & inspector mounted → ready to ship.

// The builder never certifies its own work, and the reviewer never edits. Two failed review loops = stop and ask a human — which is itself the signal that a contract needs fixing.

How changes are governed

Author here first. Export everywhere second.

Nothing changes the products directly. Every change is proposed, approved by design-system owners, updated in the vault, and only then exported into the product repositories.

Propose change → Owner approves → Vault updated → Export to product repos → Agents & engineers build

↩ Corrections from real work feed back into the vault — the brain learns from every miss.
